# UC8 — Production Execution, Actual Material Usage, Labor & Completion

## 1. Production Execution Policies & Confirmed Rules

UC8 governs the manufacturing lifecycle of queued jobs: starting production, logging actual material consumption and labor time, uploading in-progress photos, job completion, and recording actual labor costs. Owner confirmations were approved on 2026-10-19.

### Key Policies
1. **Worker Responsibilities**:
   - Any active **Worker** can start, log material usage, log labor time, upload photos, and complete any job (no rigid assignment restrictions).
   - Workers cannot view material valuation or financial totals.
2. **Admin Monitoring & Cost Entry**:
   - Admin monitors job progress and reads costs. Admin **cannot** start jobs, issue material, log labor minutes, complete jobs, or upload photos.
   - **Admin Sole Privilege**: Admin enters the final actual labor cost (`PUT /production/jobs/{id}/labor-cost`). No assumed hourly rate is applied.
3. **Job Start Requirements**:
   - Job must be in `queued` status.
   - Requires a **non-empty, fully reserved material plan** (`ready = true` in UC5) matching the current plan version.
   - Starting transitions the job to `in_progress` and records `started_at`. It **does not consume physical stock**.
4. **Incremental Actual Usage**:
   - Usage is entered incrementally (not as a cumulative replacement).
   - Usage consumes the **job's own reservation first, then genuinely free stock**.
   - Extra quantities or previously unplanned materials are permitted if free stock exists, but will **never steal another job's reservation**.
   - Decrements physical on-hand quantity and freezes unit cost at the issue moment.
5. **Job Completion & Reservation Release**:
   - Completing a job transitions it to `completed` and records `completed_at`.
   - Atomically **releases all remaining unconsumed reservations**. Because released stock was never physically issued, releasing it **does not add to physical on-hand quantity**.
   - Completion photos are optional.
6. **Labor Time Tracking**:
   - Workers record positive whole labor minutes explicitly (appended to history).
   - No stopwatch or automated clock is assumed.

## 2. API Endpoints

| Method | Path | Permission | Description |
|---|---|---|---|
| `GET` | `/production/jobs` | Admin / Worker | List queued, in-progress, and completed jobs |
| `GET` | `/production/jobs/{job_id}` | Admin / Worker | Detailed job operations (financial totals Admin-only) |
| `POST` | `/production/jobs/{job_id}/start` | Worker | Start production on a fully reserved queued job |
| `POST` | `/production/jobs/{job_id}/usage` | Worker | Log incremental actual material usage |
| `POST` | `/production/jobs/{job_id}/time` | Worker | Log actual whole labor minutes |
| `POST` | `/production/jobs/{job_id}/complete` | Worker | Mark job completed and release unused reservations |
| `PUT` | `/production/jobs/{job_id}/labor-cost` | Admin | Enter or update actual labor cost |
| `POST` | `/production/jobs/{job_id}/photos/uploads` | Worker | Initiate private upload for in-progress photo |
| `POST` | `/job-photos/{photo_id}/complete` | Worker Uploader | Complete and freeze photo in S3 |
| `GET` | `/job-photos/{photo_id}/download` | Admin / Worker / the job's customer members | Download signed private production photo. Customers outside the job get 404 (owner change 2026-11-06); ready photos are also listed as `photos` on `GET /fulfillment/jobs/{job_id}` |

### Example Payloads

**1. Start Production (`POST /production/jobs/{id}/start`)**:
```json
{
  "idempotency_key": "dbe8d729-7dd0-4374-af2c-8ed24b9a1806",
  "expected_version": 0,
  "expected_plan_version": 1
}
```

**2. Log Material Usage (`POST /production/jobs/{id}/usage`)**:
```json
{
  "idempotency_key": "57582d89-ae96-4278-b068-17835858eed1",
  "expected_version": 1,
  "note": "Steel billets issued to lathe machining",
  "lines": [
    {
      "material_id": "0f4a893a-220e-4497-8f2a-61c55f10c1b3",
      "quantity": "2.500000"
    }
  ]
}
```

**3. Log Labor Minutes (`POST /production/jobs/{id}/time`)**:
```json
{
  "idempotency_key": "30bce326-8db7-43f1-b957-c87515b63bc1",
  "expected_version": 2,
  "minutes": 180,
  "note": "Rough turning and threading"
}
```

**4. Complete Job (`POST /production/jobs/{id}/complete`)**:
```json
{
  "idempotency_key": "7132a877-380d-409e-a89e-2dbca0b1c7dc",
  "expected_version": 3
}
```

**5. Enter Actual Labor Cost (`PUT /production/jobs/{id}/labor-cost`)**:
```json
{
  "idempotency_key": "e30e1f44-d843-41bb-b5ce-6156e52c8b82",
  "expected_version": 4,
  "labor_cost": "750.00"
}
```

## 3. Database Schema & Migration 000011

- `job`: Extended with `production_version`, `started_at`, `completed_at`, and `actual_labor_cost`.
- `production_event`: Append-only audit of start, usage, time, complete, and cost events.
- `job_material_usage`: Stores actual material quantities consumed, issue-time unit costs, and rounded line totals.
- `job_time_entry`: Stores logged labor minutes, worker identity, and notes.
- `job_photo`: Stores private S3 object keys and metadata for production photos.
- `material_reservation`: Extended with `qty_consumed` to track consumed vs released quantities.

## 6. Use-Case Description Alignment (2026-11-03)

Source: `Use_Case_Description_UC1-UC12.md`. Conflicts are listed in `025-uc-spec-alignment.md`.

Matches the description: start requires a queued job with a fully reserved plan (Q8.0); status moves queued → in_progress → completed; material use creates a stock movement; a job returned from delivery goes back to in_progress (Alt-Step 1).

Conflicts kept at the confirmed rule:
- Actual labor cost: the description has the Technician enter actual cost (Q8.6). Admin enters the actual labor cost; Worker logs minutes.
- Completion photo: the description requires one. Photos are optional.
- Material consumption: the description consumes on-hand stock per issue (Q8.3) and marks each reservation `consumed` (Q8.4). The implementation consumes the job's own reservation first, then free stock, releases unused reservation at completion, and never uses another job's reservation.
- Actual time: the description stores an actual time value. The implementation stores time entries in whole minutes.
