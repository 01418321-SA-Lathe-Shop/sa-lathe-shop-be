# UC11 — Add Worker

Status: implemented, with deliberate differences from the use-case description. Recorded 2026-11-03 against `Use_Case_Description_UC1-UC12.md` (Actor: Admin). Worker management rules in `000-auth.md` and the owner decisions in the project plan remain authoritative.

## 1. Purpose

Admin creates Worker accounts so they can act as the shop's technicians in UC2 and UC5–UC9, and so their accounts can be recorded as the actor behind stock, claims and evidence.

## 2. Current behavior

| Spec step | Backend | Status |
| --- | --- | --- |
| 1–2 enter person and employee details, submit | `POST /admin/workers` (Admin) | Implemented. |
| 3.1 required fields (name, employee number, position) | Enforced by the Worker validation (`000-auth.md` §2) | Implemented. |
| 3.2 contact channel format (email and phone) | Email and phone are required for new Workers and must match the format rules (migration 000006) | Implemented. Stricter than the description, which only checks the fields are not empty. |
| 3.3 hire date not in the future | Not confirmed in the current validation | Verify. |
| 3.4 duplicate phone or email | Not enforced. Contacts are intentionally non-unique and are not login identifiers | Differs from the spec (see §4). |
| 3.5 duplicate employee number | Enforced by a unique `employee_no` | Implemented. |
| 4 save person and Worker in one transaction | Account, person and Worker profile are created together | Implemented. The spec's table names (PERSON, WORKER) map to the `account`, `person` and `worker` tables. |
| 5 list Workers | `GET /admin/workers` (Admin) | Implemented. |
| Alt-Step 3 adopt an existing person into a Worker | Not supported | Differs from the spec (see §4). |
| Deactivate and reactivate | `PATCH /admin/workers/{id}` (Admin) | Implemented. The spec's `status` (active / inactive) maps to the Worker's active flag. |
| Password | Initial password is required when creating the account; Admin may reset it. The spec has no password step | Addition required by the login model (`000-auth.md`). |

## 3. Access

Admin only. A Worker or customer calling any Worker-management endpoint receives 403.

## 4. Conflicts kept at the confirmed rule

1. Adopting an existing person (Alt-Step 3). The confirmed rule is to never adopt an unrelated account and never infer membership from a name, phone or tax ID. A Customer who should also work in the shop needs a separate, explicit Worker account.
2. Duplicate phone or email at creation (Q11.E1). Contacts are non-unique by decision (migration 000006). The description's uniqueness check would block two real people who share a family or business phone line.
3. Hire date check (3.3). Not confirmed; see §2.
