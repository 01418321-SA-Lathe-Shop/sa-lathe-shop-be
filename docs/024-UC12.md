# UC12 — Add Admin (Super Admin Registration)

Status: not implemented and not approved. Recorded 2026-11-03 against `Use_Case_Description_UC1-UC12.md` (Actor: Super Admin). Do not add an endpoint, screen or schema for this use case without a new owner decision.

## 1. What the description requires

- A Super Admin (`admin_level = super_admin`, active) checks permission (Q12.1).
- The Super Admin creates a new Admin with `admin_level = admin`, active, in one transaction with the person record (Q12.2).
- An existing person who is not yet an Admin is promoted without creating a duplicate person (Alt-Step 3, Q12.4).
- Admin lists and duplicate checks (Q12.3, Q12.E1, Q12.E2).

## 2. Why it is not implemented

- The current account roles are `admin`, `worker` and `customer` (`account_role_check`). There is no `admin_level` column and no `super_admin` role.
- The first Admin is created by the private bootstrap command (`cmd/api -bootstrap-admin`). The project rule is that there is no public or in-application route that creates an Admin.
- The confirmed staff model in `000-auth.md` describes Admin and Worker only. The source description introduces a second, higher Admin level that the owner has not confirmed.

## 3. If the owner approves it

Minimum design to decide before implementation:

1. Whether a super-admin tier is needed at all, or whether the shop owner should use the existing Admin role with the bootstrap command for further Admins.
2. Schema: add an `admin_level` (admin / super_admin) to the Admin profile, with a migration that backfills existing Admins as `admin`. Existing binaries must keep working until the migration runs (`AGENTS.md` migration rule).
3. Authorization: only an active super_admin may create or deactivate an Admin. Admin cannot promote an Admin.
4. Endpoint: `POST /admin/admins` (or equivalent) with audited creation, an initial password that is never returned, and the same contact rules as Workers.
5. Adoption of an existing person: keep it explicit (the confirmed no-adoption rule) rather than silently reusing a matching phone or email.
6. Frontend: no screen until the owner approves; `024-USECASE10-12.md` in the frontend repository records the same position.
