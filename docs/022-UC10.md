# UC10 — Unit Setting (Units and Material Conversions)

Status: partially implemented. Recorded 2026-11-03 against the use-case description `Use_Case_Description_UC1-UC12.md` (Actor: Admin). The owner-confirmed inventory rules in `005-UC5.md` remain authoritative where they differ from that description.

## 1. Purpose

Admin defines units of measure and, per material, conversion factors so that purchasing, stock, plans and usage can use the unit the shop actually handles. The material's standard unit (base unit) is the unit used for stock quantity and average cost.

## 2. Current behavior

| Spec step | Backend | Status |
| --- | --- | --- |
| Q10.1 list units | `GET /units` (Admin, Worker) | Implemented. Workers may read, which the spec does not state. |
| Q10.2 create unit | `POST /units` (Admin) | Implemented. |
| Q10.3 list materials with base unit and conversions | `GET /materials`, `GET /materials/{material_id}/conversions` (Admin, Worker) | Implemented. Conversions include deactivated records. |
| Q10.4 add conversion | `POST /materials/{material_id}/conversions` (Admin): 1 unit = `factor` base units | Implemented. |
| Q10.5 edit factor in place | Not exposed. Change a factor by deactivating the conversion and adding a new one | Differs from the spec. |
| Q10.6 rename unit | Not exposed | Not implemented. |
| Deactivate conversion (no spec step) | `POST /materials/{material_id}/conversions/{conversion_id}/deactivate` (Admin) | Implemented; repeating it returns the original record. |

Units are not deleted. Existing stock, reservations and history keep their recorded unit.

## 3. Spec rules to keep

- A conversion's target unit is always the material's base unit; `from` and `to` may not be equal.
- One active conversion per (material, from unit) pair. Duplicate pairs are rejected, and the description directs the user to change the existing conversion instead.
- Unit names are trimmed and compared case-insensitively for duplicates.

Verify before relying on these: the duplicate-name and duplicate-pair checks were not confirmed by reading the current validation code during this alignment.

## 4. Gaps and decisions

1. Rename unit (Q10.6): not implemented. Renaming would change the label of historical records, so it needs a decision on whether history shows the name at the time of the movement.
2. Edit factor (Q10.5): not implemented. The current deactivate-and-add approach keeps every factor used in history immutable. Keep this unless the owner asks for in-place edits.
3. The description gives Admin only for listing units. Workers can read units and conversions today because UC5 plans and purchasing show them; keep this unless the owner restricts it.

Money and quantity precision are unchanged: quantities and unit costs use `NUMERIC(18,6)`.
