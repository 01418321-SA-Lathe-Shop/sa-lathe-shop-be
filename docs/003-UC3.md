# UC3 — Customer Quotation Decisions & Acceptance Terms

## 1. Business Rules & Decision Workflow

In UC3, customers review sent quotations and record an acceptance or rejection decision. All endpoints require Bearer authentication.

### Decision Authority
- **Any Active Member**: Any current active member of a company may accept or reject a quotation for that company. The deciding actor does not need to be the company owner or the user who created the request.
- **Admin/Worker**: Staff have read-only access to decision records and cannot submit decisions.

### Rejection Threshold & Automatic Cancellation
- **Rejection Counter**: The system counts distinct customer rejection audits across all revisions of a request.
- **Revision Permissions**: Customer rejections 1 through 5 reject the specific quotation and allow Workers to create and send a revised quotation in UC2.
- **6th Rejection Cancellation**: The **6th customer rejection** atomically sets the parent request status to `canceled` and permanently prevents any further revisions.
- *Distinction*: Worker request refusal under UC2 is separate and does not count toward the customer rejection threshold.

---

## 2. Persisted Acceptance Terms

When a quotation is accepted, the system atomically computes and freezes immutable acceptance terms:

| Customer Type | Total Price | Required Deposit | PO Required |
|---|---|---|---|
| `individual` | Any amount | **50% deposit**, rounded upward to satang | No |
| `company` | $\le$ THB 10,000.00 | **None** | **Yes** |
| `company` | $>$ THB 10,000.00 | **50% deposit**, rounded upward to satang | **Yes** |

### Submission Deadline
- The system captures `accepted_at` and sets `documents_due_at` to **exactly 336 hours (14 days)** later.
- Acceptance terms are immutable historical snapshots and are never recalculated if customer profile details change later.
- The balance after deposit is calculated as `final_price - deposit_amount`.

## 3. API Endpoints

| Method | Path | Permission | Description |
|---|---|---|---|
| `POST` | `/quotations/{quotation_id}/decision` | Active Customer Member | Accept or reject latest sent quotation |
| `GET` | `/quotations/{quotation_id}/decision` | Customer Member / Staff | Read recorded decision and calculated terms |
| `GET` | `/requests/{request_id}/quotation-decisions` | Customer Member / Staff | Paginated list of decision history |

### Example Payloads

**1. Accept Quotation**:
```json
{
  "outcome": "accept",
  "expected_lock_version": 2
}
```
*Note: Acceptance bodies cannot include a non-empty reason.*

**2. Reject Quotation**:
```json
{
  "outcome": "reject",
  "reason": "Estimated price exceeds our department budget for this tooling",
  "expected_lock_version": 2
}
```
*Note: Reason is trimmed, 1–2,000 Unicode characters.*

### Idempotency & Replay Semantics
- Replaying the exact same request (same actor, outcome, normalized reason, and lock version) returns the saved decision snapshot without incrementing the rejection count or altering deadlines.
- Any conflicting decision, altered payload, or attempt by a different user returns HTTP 409 Conflict.

## 4. Database Schema & Migration 000005

- `quotation_decision`: Records `quotation_id`, `actor_id`, `outcome` (`accept`/`reject`), optional `reason`, `decided_at`, and `rejection_sequence_number`.
- `quotation_acceptance_terms`: Linked to accepted decisions; stores `customer_type`, `final_price`, `deposit_required`, `po_required`, `deposit_amount`, `balance_after_deposit`, `accepted_at`, and `documents_due_at`.

## 6. Use-Case Description Alignment (2026-11-03)

Source: `Use_Case_Description_UC1-UC12.md`. Conflicts are listed in `025-uc-spec-alignment.md`.

Matches the description: only a `sent` quotation can be decided; approval records the decision; terms follow customer type and amount (individual → deposit; company ≤ THB 10,000 → PO only; company > THB 10,000 → PO and deposit); a rejected quotation is revised by the Worker in UC2; repeated rejection cancels the request.

Conflicts kept at the confirmed rule:
- Cancellation happens on the 6th customer rejection, not the 5th (Q3.6). Rejections 1 through 5 allow revision.
- The description says terms are derived and not stored (design note, step 5.2). The implementation stores an immutable acceptance-terms snapshot (`quotation_acceptance_terms`) because confirmed terms are immutable.
- The description counts quotations on the request (Q3.4). The implementation counts distinct customer rejection audits across all revisions.
